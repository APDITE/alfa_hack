# scoring

Сервис оценки риска: по данным компании, кредитной истории и параметрам заявки возвращает вероятность дефолта, класс риска и список факторов с направлением влияния. Решение (одобрить, другие условия, уточнение, отказ) он не принимает, это делают кредитные правила бэкенда.

## Запуск

```bash
uv sync                                   # зависимости по uv.lock, Python 3.12
uv run uvicorn app.main:app --port 8000   # сервис
uv run pytest                             # тесты
```

В compose сервис называется `scoring`, бэкенд ходит на `http://scoring:8000`. Swagger: `/docs`, проверка живости: `GET /health`.

Переменные окружения:

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `SCORECARD_CONFIG` | `config/scorecard.yaml` | путь к файлу балльной карты |

## Контракт

`POST /score`

```json
{
  "application": {"product_id": "working_capital", "amount": 1500000, "term_months": 12},
  "company": {"inn": "7700000001", "okved": "47.11", "age_months": 79,
              "revenue_year": 48000000, "expenses_year": 40000000, "liabilities_total": 4000000},
  "credit_history": {"active_loans": 1, "overdue_count": 0, "max_overdue_days": 0}
}
```

Ответ:

```json
{
  "score": 0.0165,
  "risk_class": "low",
  "points_total": 820,
  "factors": [
    {"name": "credit_history", "points": 120, "impact": "decreases_risk", "comment": "просрочек в кредитной истории нет"}
  ],
  "model_version": "scorecard-0.1.0"
}
```

- `product_id`: `working_capital` или `equipment`. Скоринг от продукта не зависит, это сознательно: одна и та же оценка риска должна давать разные условия через правила бэкенда (сценарий 8).
- Лишние поля во входе игнорируются. Невалидный вход (отрицательная сумма, неизвестный продукт, нецифровой ИНН) даёт 422.
- Факторы идут от самого влиятельного к наименее. Фактор с нулём баллов в список не попадает.
- `score` округлён до 4 знаков, расчёт детерминирован: одинаковый вход всегда даёт одинаковый ответ.

## Как считается оценка

```
points_total = base_points + сумма баллов факторов
score = clamp(1 / (1 + exp(slope * (points_total - pivot))), min_pd, max_pd)
```

Чем больше баллов, тем надёжнее заёмщик. Параметры шкалы подобраны так, чтобы PD демо-компаний совпали с ориентирами из `docs/scenarios.md` (подробнее в README моков). Класс риска: `low` при score ниже 0.10, `medium` ниже 0.25, иначе `high`.

Факторы (все веса и границы в [config/scorecard.yaml](config/scorecard.yaml)): просрочки (максимальная и количество), долговая нагрузка (обязательства к выручке), рентабельность, возраст компании, размер выручки, сумма заявки к выручке, число действующих кредитов, срок.

Менять карту можно без правки кода. Битый конфиг (неупорядоченные интервалы, неизвестный признак) валится на старте сервиса, а не на первом запросе.

## Почему балльная карта

- Объяснимость: каждый фактор даёт конкретные баллы и комментарий, сотрудник банка и клиент видят причину.
- Меток "вернул или не вернул" у нас нет, обучать на них нечего. Градиентный бустинг или регрессия на синтетике выучили бы только закономерности, которые мы сами заложили в генератор.
- Балльная карта это привычный для банка формат, её веса согласуются с риск-менеджером без пересборки модели.

## Ограничения

- Веса заданы экспертно и не калиброваны на реальных дефолтах. `score` это не откалиброванная вероятность, а монотонная шкала риска, приведённая к виду вероятности.
- Нет учёта отрасли (ОКВЭД принимается, но в расчёте не участвует), залога и динамики показателей по периодам.
- Нулевая выручка трактуется как максимальный риск.

## Что дальше

Когда появятся реальные данные: заменить карту на логистическую регрессию с WoE-биннингом (контракт `/score` не изменится), добавить калибровку и мониторинг стабильности (PSI), версионировать карты через `model_version`.
