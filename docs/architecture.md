| Компонент | Технологии | Отвечает за |
| --- | --- | --- |
| `frontend` | React 19, TypeScript, Vite | Кабинет клиента: регистрация по ИНН, каталог и подбор продукта, заявка, статус, предложение, уточнения, подписание, уведомления. Рабочее место сотрудника: очереди, карточка заявки, решение. |
| `backend` | Python 3.12, FastAPI, SQLAlchemy 2, Alembic, PyJWT, bcrypt | API, авторизация и права, регистрация (карточка компании из реестра), действия клиента и сотрудника, кредитные правила, предодобрение и график платежей, уведомления. Единственная точка смены статуса — `lifecycle.transition`. |
| `worker` | тот же код, `python -m app.worker` | Автоматические этапы: проверка полноты, обогащение из внешних источников, скоринг, кредитное решение. Можно запускать несколько копий. |
| `scoring` | FastAPI, балльная карта в YAML | Оценка риска: PD, класс риска, факторы с баллами. Решение не принимает. |
| `mocks` | FastAPI, синтетические данные | Внешние источники с теми же контрактами, переключатель доступности для демо сбоев. |
| `db` | PostgreSQL 16 | Заявки, история переходов (аудит), проверки, оценки, решения, очередь задач, уведомления. |

## Как заявка проходит конвейер

```mermaid
sequenceDiagram
    actor C as Клиент
    participant API as backend API
    participant DB as PostgreSQL
    participant W as worker
    participant M as mocks
    participant S as scoring
    actor E as Сотрудник

    C->>API: POST /applications (черновик)
    C->>API: POST /applications/{id}/submit + Idempotency-Key
    API->>DB: статус submitted, задача в pipeline_jobs, уведомление клиенту
    loop каждую секунду
        W->>DB: SELECT … FOR UPDATE SKIP LOCKED
    end
    W->>DB: data_check: полнота заявки
    W->>M: ЕГРЮЛ, «Прозрачный бизнес», БКИ
    alt источник не отвечает
        W->>DB: повтор через 5, 15, 45 с, затем раз в минуту, после 10 попыток — сотруднику
    end
    W->>S: POST /score
    W->>DB: кредитные правила → одобрение / другие условия / уточнение / ручная проверка / отказ
    C->>API: GET /applications/{id} (опрос каждые 2 с, пока работает конвейер)
    opt ручная проверка
        E->>API: POST /applications/{id}/decision
    end
    C->>API: принять условия, подписать (симуляция)
```

## Ключевые решения

| Решение | Почему | Ограничение и развитие |
| --- | --- | --- |
| Статус меняется только в `lifecycle.transition` | Переходы проверяются по одной таблице, каждый ход пишется в историю, уведомления клиента и задачи конвейера создаются в той же транзакции. | — |
| Очередь задач в PostgreSQL (`FOR UPDATE SKIP LOCKED`) | Не нужен отдельный брокер: меньше компонентов для проверки, задачи и смена статуса атомарны, воркеры масштабируются горизонтально. | При росте нагрузки — брокер (Kafka/RabbitMQ) по тому же контракту этапов. |
| Ретраи внешних источников с backoff, затем передача сотруднику | Заявка не теряется и не зависает при сбое ЕГРЮЛ или БКИ; клиент видит, что ждём внешнюю службу. Непредвиденная ошибка этапа повторяется трижды, затем заявку получает сотрудник с пометкой в истории. | Отдельный счётчик попыток для сбоев и ошибок, повторный запуск этапа из рабочего места. |
| Идемпотентная отправка (`Idempotency-Key`) | Повторный клик или ретрай сети не создаёт вторую заявку и второй набор задач. | — |
| Скоринг отдельно от кредитного решения | Одна оценка риска даёт разные условия для разных продуктов (сценарий 8); правила меняются без пересборки модели. | Балльная карта не калибрована на реальных дефолтах (см. `scoring/README.md`). |
| Продукты, пороги и балльная карта — в YAML | Риск-менеджер меняет параметры без правки кода; битый конфиг останавливает старт сервиса, а не запрос. | Версионирование конфигов и согласование изменений. |
| Внешние сервисы — моки с теми же контрактами | Проверяемая версия автономна, без доступа к системам банка и платных API. | Замена на реальные интеграции через тот же протокол `Integrations`. |
| Предодобрение — те же источники, скоринг и `decide`, без хранения | Предложение не расходится с решением конвейера: заявка на предложенные условия одобряется автоматически (это проверяет тест). Наибольшая сумма ищется бинарным поиском, расчёт — десятки миллисекунд. | Каждый показ — несколько десятков запросов к скорингу; при нагрузке — кэш на день или расчёт по расписанию. |
| График платежей считает бэкенд | Платёж берётся из решения, поэтому график совпадает с условиями в предложении, в том числе со ставкой сотрудника. | Досрочное погашение и пересчёт графика — после учёта фактических платежей. |
| Регистрация по ИНН берёт карточку компании из реестра синхронно | Клиент вводит только имя, логин и пароль; реквизиты не расходятся с тем, что потом проверит конвейер. Если реестр не отвечает — 503 и понятное сообщение, а не учётная запись без компании. Финансы при регистрации не спрашиваются: конвейер запросит их уточнением, если в «Прозрачном бизнесе» нет данных. | Подтверждение личности и полномочий (Госуслуги, электронная подпись), несколько пользователей компании. |
| Два режима compose: разработка и стенд | `make up` — Vite и `--reload` с исходниками в томах для разработки; `make up-prod` — фронтенд собран в статику, бэкенд и воркер из `prod`-стадий от непривилегированного пользователя, перезапуск после сбоя, свой секрет JWT. | TLS и секреты в хранилище — на стороне площадки размещения. |

## Наблюдаемость

`backend/app/ops.py` считает состояние конвейера из базы: очередь задач и возраст самой
старой готовой задачи, заявки без движения, ожидание внешних сервисов, технические ошибки
этапов, решения по исходам. Оно отдаётся в двух видах: `GET /metrics` для Prometheus
(правила — `monitoring/alerts.yml`) и `GET /api/ops/summary` для виджета в рабочем месте
сотрудника. Пороги одинаковые, поэтому виджет и алерты не расходятся.

## Безопасность

- Пароли — bcrypt, доступ — JWT (HS256) со сроком жизни 12 часов.
- Права проверяются на бэкенде: клиент видит только заявки своей компании (чужая — 403), сотрудник не видит черновики, решение принимает только сотрудник и только на ручной проверке.
- Вне `APP_ENV=development` API не стартует с секретом JWT по умолчанию.
- Все данные синтетические, доступа к системам Альфа-Банка и государственным сервисам нет.
- Регистрация: пароль от 8 символов, логин уникален, одна учётная запись на компанию (повторная регистрация — 409). Личность и полномочия заявителя в прототипе не проверяются.
- Демо-допущения: тестовые пароли совпадают с логином, `/mock/admin` открыт для демонстрации сбоев. `make up` запускает контейнеры в dev-режиме (Vite и `--reload`), `make up-prod` — в режиме стенда: фронтенд в статике, бэкенд от непривилегированного пользователя, `APP_ENV=production`.
